## Context

- Набор камер мониторинга (`config.MONITOR_CAMERAS`) читается один раз в
  `WorkerRegistry.start_monitoring()`: при старте и после входа в аккаунт. Порог
  (`config.MATCH_THRESHOLD`) `Recognizer.match()` читает на каждом распознавании.
  Оба значения приходят из окружения при импорте `config`.
- В БД уже есть таблица `settings (key, value)`, в ней лежит `unlock_mode`.
- Воркер камеры бывает постоянным (`persistent=True`) или «по требованию». Второй
  останавливается сам, когда зрителей нет дольше `WORKER_IDLE_TIMEOUT`. Флаг
  `persistent` уже можно поднимать на лету (просмотр становится мониторингом).
- Распознаватель работает в потоке каждой камеры, по 3 раза в секунду на лицо.

## Goals / Non-Goals

**Goals:**
- Одно место, где решается, какое значение действует: значение из UI, если оно
  задано, иначе значение из окружения.
- Применение без перезапуска и без лишних переподключений к видеосерверу.

**Non-Goals:**
- Общий механизм настроек для всех параметров `config`.
- Повтор запуска мониторинга, если при старте Росдомофон недоступен (отдельная задача).

## Decisions

**Хранение: ключи `monitor_cameras` и `match_threshold` в `settings`.**
`monitor_cameras` хранится как JSON-массив id, `match_threshold` как строка с
числом. Если ключа нет, значит в UI ничего не задано и действует окружение. Сброс
удаляет ключ. Пустой массив `[]` тоже валидное значение: мониторинг выключен. Его
нужно отличать от «не задано», поэтому в API `null` означает сброс, а `[]` —
пустой набор.
Альтернатива: отдельный JSON-файл в `data/`. Отклонена: таблица уже есть, и
`unlock_mode` хранится так же.

**Кэш в памяти `Store`.** Значения читаются из SQLite в конструкторе и
обновляются в сеттерах. Геттеры отдают кэш без запроса к БД и без блокировки, а
порог читается из потоков всех камер на каждом распознавании. Других писателей в
БД нет (процесс один), так что кэш не устареет.

**Разрешение значений.** `Store` знает только то, что задано в UI
(`monitor_cameras() -> list[int] | None`, `match_threshold() -> float | None`).
Действующее значение вычисляют потребители: `Recognizer` подставляет
`config.MATCH_THRESHOLD`, если в UI ничего нет, а `WorkerRegistry` — свой
`config.MONITOR_CAMERAS`. `None` в окружении по-прежнему означает «все камеры».
Тесты при этом подменяют `config` через `monkeypatch`, как и сейчас.

**Применение набора: `WorkerRegistry.start_monitoring()` → `sync_monitoring()`.**
Метод идемпотентный: берёт список камер аккаунта, вычисляет действующий набор,
запускает постоянные воркеры для недостающих камер (уже работающему воркеру
просмотра просто поднимает `persistent`) и снимает `persistent` с постоянных
воркеров вне набора. Воркер без флага ведёт себя как воркер просмотра: если
зрителей не было дольше `WORKER_IDLE_TIMEOUT`, он останавливается на ближайшей
проверке `_idle()` (не позже ~1 с), а если камеру смотрят, работает до закрытия.
Вызывается при старте, после входа и после сохранения набора в UI.
Альтернатива: останавливать исключённые воркеры сразу через `stop()`. Отклонена:
это оборвало бы открытый просмотр.

**API.** `GET /api/settings` возвращает действующие значения, значения по
умолчанию и источник:
```json
{"monitor_cameras": [12034] | null, "monitor_cameras_default": [1001] | null,
 "monitor_cameras_source": "ui" | "default",
 "match_threshold": 0.4, "match_threshold_default": 0.363,
 "match_threshold_source": "ui" | "default"}
```
Здесь `null` у `monitor_cameras` означает «все камеры аккаунта». `PUT
/api/settings` делает частичное обновление: поле отсутствует — не трогать,
`null` — сброс, иначе значение. Отличаем отсутствие поля от `null` через
`model_fields_set` у pydantic. Как и в `PUT /api/unlock`, сначала всё
проверяется, потом применяется. Порог должен быть в диапазоне `[0, 1]`, id камер
— существовать в аккаунте (проверка через `client.cameras()`; без входа будет
401, как у других вызовов Росдомофона). После записи набора, если вход
выполнен, вызывается `sync_monitoring()`. Ответ совпадает с `GET`.

**Предупреждение о несуществующих камерах вычисляет UI.** Вкладка всё равно
загружает `/api/cameras` и `/api/status`, поэтому разница «действующий набор
минус камеры аккаунта» считается в браузере. Так `GET /api/settings` обходится
без запроса к Росдомофону и работает без входа.

**UI: вкладка «Настройки».** Две секции, у каждой свои «Сохранить» и «По
умолчанию»:
- «Камеры мониторинга»: строка на каждую камеру аккаунта с чекбоксом, названием и
  id, состоянием из `/api/status` («анализ идёт», «подключение…», «не
  анализируется», текст ошибки), подпись источника («задано здесь» / «по
  умолчанию из ROSDOMOFON_MONITOR_CAMERAS» / «по умолчанию: все камеры») и
  предупреждение о камерах набора, которых нет в аккаунте. Если действует «все»,
  отмечены все чекбоксы. Сохранение всегда отправляет явный список.
- «Порог узнавания»: `<input type=number min=0 max=1 step=0.01>`, значение по
  умолчанию и подсказка: выше — меньше ложных узнаваний и больше «Неизвестный».

## Risks / Trade-offs

- [Набор в UI «перекрывает» окружение, и правка env потом ни на что не влияет] →
  UI показывает источник значения, есть кнопка «По умолчанию», README это
  описывает.
- [При сохранении явного списка новая камера аккаунта не попадёт в мониторинг
  автоматически, хотя при «все камеры» попала бы] → это ожидаемо для явного
  выбора; чтобы вернуться к «все камеры», есть сброс, если env не задан.
- [Слишком низкий порог из UI ведёт к ложным узнаваниям, а при включённом
  открытии двери откроет её чужому] → подсказка в UI. Режим «dry_run» и журнал
  «открыл бы» уже есть для проверки порога.
- [Гонка: `sync_monitoring()` одновременно из обработчика входа и из PUT] →
  запуск и правка флагов идут под `_lock` реестра, а повторный вызов
  идемпотентен.

## Migration Plan

Миграция схемы не нужна. После обновления поведение прежнее, пока в UI ничего не
сохранено. Откат на старую версию просто игнорирует новые ключи в `settings`.
