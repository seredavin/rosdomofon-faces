## Context

Мотивация — в proposal.md. Текущее состояние: конвейер кадра (`app/pipeline.py`)
ведёт треки и голосование; статус трека становится «знакомый» после ≥3
голосов. Хранилище — SQLite без механизма миграций. Клиент Росдомофона умеет
вход, токены и камеры, но не ключи.

Открытие двери в Росдомофоне (по HA-интеграции, `lock.py`):
- `GET /abonents-service/api/v2/abonents/keys` → `[{adapterId, relay, type, ...}]`,
  `type`: 1 — дверь подъезда, 2 — шлагбаум, 3 — ворота, 4 — калитка;
- `POST /rdas-service/api/v1/rdas/{adapterId}/activate_key` с телом `{"rele": relay}`,
  успех — HTTP 200.

У обеих камер аккаунта одинаковый `rdaUid`, поэтому автоматически сопоставить
камеру и дверь нельзя — привязку делает пользователь.

## Goals / Non-Goals

**Goals:**
- Открытие по событию «появление стало знакомым», без влияния на темп анализа
  кадров в обычном режиме.
- Безопасные умолчания: режим «только журнал», нет разрешений, нет привязок.
- Переключение режима и разрешений без перезапуска.

**Non-Goals:**
- Liveness, отдельный строгий порог для двери (решение пользователя; риск — ниже).
- Управление дверью вручную из интерфейса (это делает приложение Росдомофона и
  HA-интеграция).

## Decisions

### Где принимается решение: хук в конвейере
`Track.add_vote()` уже вычисляет статус. Конвейер после голосования проверяет
переход статуса в «знакомый» при `track.unlock_result is None` и вызывает
`DoorUnlocker.try_unlock(camera_id, person_id)`. Результат сохраняется в
треке и попадает в событие при его записи. Так «один раз на появление»
получается естественно: у трека уже есть результат.

Если знакомый сначала получил статус без разрешения, а затем ему дали
разрешение, — в этом появлении повторной проверки нет (проверка один раз при
переходе статуса). Это проще и безопаснее.

### `DoorUnlocker`: один на сервис, потокобезопасный
Хранит время последнего открытия по двери и под блокировкой «резервирует»
дверь до вызова Росдомофона — две камеры, привязанные к одной двери, не
откроют её дважды. Порядок проверок: режим ≠ «выключено» → у камеры есть
привязка → у человека есть разрешение → дверь не в паузе 30 с → по режиму
либо «открыл бы», либо реальный вызов. Возвращает `None`, если открытие не
положено (ничего не записывается), или результат `would_open` / `opened` /
`failed`.

Пауза 30 с ставится и при `would_open`: журнал «только журнал» должен
показывать ровно то, что произошло бы в режиме «открывать».

### Вызов Росдомофона синхронно, с таймаутом 5 с
Вызов делается в потоке воркера камеры. Открытия редки, а очередь пакетов и
сброс отсчёта PTS (уже есть) поглощают паузу: картинка догоняет реальное
время. Асинхронный вызов усложнил бы запись результата в событие, которое
могло бы завершиться раньше ответа.
- 401 → обновить токен и повторить один раз (как для остальных запросов);
  прочие ошибки → `failed`, без повторов в этом появлении.

### Хранилище: простые миграции схемы
Первая миграция в проекте: при открытии БД `PRAGMA table_info` и
`ALTER TABLE … ADD COLUMN`, если столбца нет.
- `persons.can_unlock INTEGER NOT NULL DEFAULT 0`;
- `events.unlock TEXT NULL` (`would_open` / `opened` / `failed`);
- новая `settings(key PRIMARY KEY, value)` — режим `unlock_mode`;
- новая `camera_doors(camera_id PRIMARY KEY, adapter_id, relay, door_name)`.

Привязка хранит и `door_name` — чтобы показывать её, даже если список ключей
временно недоступен.

### Двери в API
- `GET /api/doors` — ключи аккаунта: `{id: "<adapterId>:<relay>", name, type}`.
- `GET /api/unlock` → `{mode, bindings: {camera_id: door | null}}`;
  `PUT /api/unlock` — частичное обновление режима и/или привязок.
- `PATCH /api/persons/{id}` принимает `name` и/или `can_unlock`.
- `GET /api/events` — поле `unlock` у событий и фильтр `unlocked=true`.

### Интерфейс
- Новая вкладка «Двери»: режим (три варианта) и выбор двери для каждой камеры,
  с предупреждением о рисках рядом с режимом «открывать».
- «Люди»: переключатель «может открывать дверь».
- «Журнал»: значок результата открытия и фильтр «только с открытием».

## Risks / Trade-offs

- [Фото жильца на телефоне откроет дверь — liveness нет] → разрешение только
  явно выбранным людям; режим «только журнал» по умолчанию; быстрое выключение;
  каждое открытие видно в журнале со снимком. Риск остаётся — пользователь
  предупреждён.
- [Ложное узнавание при пороге 0.363] → отдельного порога для двери нет (решение
  пользователя). Перед включением «открывать» — неделю смотреть журнал «открыл
  бы»; при ложных срабатываниях поднять `ROSDOMOFON_MATCH_THRESHOLD`.
- [Дверь общая для подъезда] → пауза 30 с и одно открытие на появление не
  дают держать дверь открытой.
- [Блокировка потока воркера на время вызова] → таймаут 5 с, вызовы редки.
- [Росдомофон может изменить API ключей] → ошибки видны в журнале как
  `failed` и в логе.

## Migration Plan

Миграция схемы выполняется автоматически при старте и только добавляет
столбцы и таблицы. Откат кода оставляет лишние столбцы — старый код их
игнорирует.
