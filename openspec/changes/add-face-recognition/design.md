## Context

Сейчас (см. proposal.md — Why) `CameraWorker` в `app/stream.py` запускается при
первом зрителе, читает HLS в отдельном потоке, выравнивает кадры по PTS, раз в
≤100 мс запускает YuNet и кодирует каждый кадр в JPEG для MJPEG. Через 30 с без
зрителей воркер останавливается. Хранилища, кроме `data/token.json`, нет.

Ограничения, влияющие на решения:
- Поток камер — SD, около 704 px в ширину. Лица у двери небольшие, точность
  распознавания ограничена разрешением.
- Сервис однопользовательский, слушает localhost, работает на одной машине.
- Новые pip-зависимости нежелательны: OpenCV уже содержит и YuNet, и SFace
  (`cv2.FaceRecognizerSF` проверен на установленном OpenCV 5.0).

## Goals / Non-Goals

**Goals:**
- Конвейер на кадр: детекция → трекинг → (фильтр качества → распознавание) →
  голосование, один на камеру, общий для мониторинга и просмотра.
- Минимальная нагрузка в фоне: без зрителей кадры не кодируются в JPEG.
- Одно хранилище для людей, образцов и событий с простой автоочисткой.

**Non-Goals:**
- Многопоточный/распределённый анализ, GPU.
- Переобучение модели или автоматическое пополнение образцов по распознанным
  лицам (риск «дрейфа» базы).
- Миграции схемы БД: это первая версия схемы.

## Decisions

### Распознавание: SFace + косинусное сходство по всем образцам
`FaceRecognizerSF.alignCrop()` по 5 точкам YuNet → `feature()` → вектор 128,
нормируется. Все образцы держатся в памяти матрицей `N×128`; сходство с базой —
одно матричное умножение, для человека берётся максимум по его образцам. Порог
по умолчанию 0.363 (рекомендация авторов SFace для косинуса), настраивается.
- Почему не InsightFace/ArcFace: точнее, но тяжелее (onnxruntime, 100+ МБ) и
  готовые модели только для некоммерческого использования.
- Почему не векторная БД: людей и образцов десятки-сотни, перебор быстрее и
  проще.

`FaceRecognizerSF` и `FaceDetectorYN` не потокобезопасны — по экземпляру на
воркер. Матрица образцов общая, неизменяемая: при изменении базы собирается
новая и атомарно подменяется (счётчик версии), воркеры подхватывают её на
следующем кадре — так выполняется «без перезапуска» из face-enrollment.

### Трекинг: жадное сопоставление по IoU
Детекции текущего кадра сопоставляются с активными треками по IoU рамок
(жадно, по убыванию IoU, порог 0.3); несопоставленные детекции открывают новые
треки. Трек завершается, если не обновлялся дольше `TRACK_TIMEOUT` (2 с).
- Почему не SORT/ByteTrack: на дверной камере 1–3 лица одновременно, детекция
  10 раз в секунду, люди двигаются медленно — IoU хватает, а фильтр Калмана и
  зависимости не нужны.

### Голосование: скользящее окно
Распознаются только пригодные лица и не чаще 3 раз в секунду на трек. Каждый
результат — голос «человек X» или «незнакомый». Пока голосов меньше 3, статус
трека — «определяется». Дальше статус — большинство среди последних 7 голосов;
при равенстве остаётся прежнее значение. Это даёт устойчивость к единичным
ошибкам и при этом позволяет исправить ранний неверный вывод.

### Фильтр качества и выбор лучшего кадра
Лицо пригодно, если одновременно:
- меньшая сторона рамки ≥ `MIN_FACE_SIZE` (по умолчанию 40 px — компромисс для
  SD-потока; SFace работает на 112×112);
- фронтальность: смещение носа от середины между глазами ≤ 0.35 межглазного
  расстояния, наклон линии глаз ≤ 25°;
- резкость: дисперсия лапласиана выровненного кадра ≥ `MIN_SHARPNESS`.

Оценка качества = уверенность детектора × размер × резкость (нормированные).
Для трека запоминается кадр с лучшей оценкой: вырезка лица с полями (рамка
×1.6) для снимка и вектор этого кадра. Пороги резкости и размера калибруются на
реальных камерах (см. Open Questions).

### Событие = трек
Завершённый трек, в котором было хотя бы одно пригодное лицо, записывается как
событие: камера, начало, конец, итоговый статус голосования (человек или NULL),
снимок лучшего кадра. Вектор лучшего кадра сохраняется только у событий
незнакомых — он нужен, чтобы превратить карточку в образец. У знакомых вектор
не храним (меньше биометрии).

Галерея незнакомых — это события с `person_id IS NULL`. Поэтому:
- назначение имени = создать образец (копия вектора и снимка) и проставить
  `person_id` у события, вектор у события удаляется;
- отклонение карточки = удаление события целиком (вместе со снимком и
  вектором) — оно же пропадает и из журнала;
- срок хранения события определяется его текущим статусом: после назначения
  имени действует срок знакомых.

У образца собственная копия снимка, чтобы очистка событий не задевала образцы.

### Хранилище: SQLite + файлы снимков
`data/faces.db` (stdlib `sqlite3`, WAL, одно соединение под блокировкой):
- `persons(id, name UNIQUE, created_at)`;
- `samples(id, person_id → persons ON DELETE CASCADE, embedding BLOB, image, created_at)`;
- `events(id, camera_id, started_at, ended_at, person_id → persons ON DELETE SET NULL, image, embedding BLOB NULL)`.

Снимки — JPEG в `data/faces/events/` и `data/faces/samples/`, в БД — имя
файла. Время — UTC epoch-секунды, в интерфейсе — локальное. Удаление человека
переводит его события в «незнакомые» без вектора: в галерее они не
показываются (нет вектора — нельзя сделать образец), в журнале видны как
«Неизвестный».
- Почему не JSON-файлы: нужны фильтры журнала, постраничная выдача и
  транзакционность назначения имени.

### Мониторинг: постоянные воркеры + режим «по требованию»
`WorkerRegistry` получает набор камер мониторинга (`MONITOR_CAMERAS`, по
умолчанию все). Постоянные воркеры не останавливаются по простою; воркеры
камер вне набора работают как сейчас — до 30 с после последнего зрителя.
Запуск — в `lifespan` при наличии токена и после успешного входа; остановка —
при выходе. `AuthError` в воркере останавливает его со статусом «нужен вход».

Без зрителей воркер не рисует рамки и не кодирует JPEG: признак «есть зритель»
— обращение к MJPEG/faces за последние 5 с. Выравнивание по PTS остаётся (оно
же задаёт темп анализа), детекция — те же ≤10 раз в секунду.

### Настройки
Через переменные окружения с префиксом `ROSDOMOFON_` в `app/config.py`:
`MONITOR_CAMERAS`, `MATCH_THRESHOLD`, `MIN_FACE_SIZE`, `MIN_SHARPNESS`,
`TRACK_TIMEOUT`, `UNKNOWN_RETENTION_DAYS` (7), `KNOWN_RETENTION_DAYS` (30).

### API (новое и изменённое)
- `GET /api/status` — состояние воркеров.
- `GET /api/cameras/{id}/faces` — плюс `track_id`, `status`, `person`.
- `GET /api/events?camera_id&person_id&unknown&since&until&before_id&limit` →
  `{items, next_before_id}` (курсор по id: новые события не сдвигают страницы).
- `GET /api/events/{id}/image`, `DELETE /api/events/{id}`,
  `POST /api/events/{id}/assign` `{person_id}` или `{name}`.
- `GET/POST /api/persons`, `PATCH/DELETE /api/persons/{id}`,
  `DELETE /api/samples/{id}`, `GET /api/samples/{id}/image`.

Интерфейс — вкладки «Видео», «Незнакомые», «Люди», «Журнал» в том же
`index.html`.

### Тесты
Добавляется `pytest` (dev-зависимость). Модульные тесты: трекер, голосование,
фильтр качества, хранилище и очистка, API через `TestClient`. Распознавание
end-to-end на синтетике не проверить — проверяется вручную на камерах.

## Risks / Trade-offs

- [SD-разрешение: лица мелкие, ложные «Неизвестный»] → порог размера
  настраивается; рекомендовать 5–10 образцов на человека в разных условиях;
  голосование сглаживает единичные промахи.
- [Ложное узнавание соседа как знакомого] → порог выше рекомендованного можно
  задать настройкой; распознавание не управляет замком.
- [Постоянная нагрузка CPU/сети] → без зрителей нет JPEG-кодирования; набор
  камер настраивается.
- [Рост БД и снимков] → почасовая очистка; один снимок на появление.
- [Биометрия соседей] → векторы незнакомых живут ≤7 дней и только для
  карточек; у знакомых событий векторов нет; всё локально.
- [Потеря данных при сбое] → SQLite WAL; запись события — одна транзакция,
  файл снимка пишется до вставки строки, «сироты» подчищает очистка.

## Migration Plan

Новая БД создаётся при первом запуске; модель SFace скачивается с проверкой
SHA-256, как YuNet. Откат — вернуть предыдущий коммит; `data/faces.db` и
`data/faces/` можно удалить без последствий для входа.

## Open Questions

- Конкретные значения `MIN_SHARPNESS` и `MIN_FACE_SIZE` для этих камер —
  подбираются после первых дней работы по логам качества; на спецификацию и
  структуру задач не влияют.
